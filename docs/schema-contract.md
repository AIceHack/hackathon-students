# Контракт модели marketplace

**Статус: проект для согласования участниками №2–5.** Правила ниже — общий
исходный интерфейс; фактическое подтверждение и результаты сборки пока не
получены. Изменения согласуются с владельцами затронутых модулей и фиксируются
здесь до интеграции.

## Общие правила

- PostgreSQL 16; источник — восемь таблиц `raw`. Бизнес-поля `raw` не менять.
- Ответы на пять официальных вопросов строятся из `core`; `mart` не требуется
  для их выполнения. Витрины и дополнительная аналитика читают только `core`.
- Все идентификаторы и почтовые префиксы — `text`; денежные суммы —
  `numeric(14,2)`, порядковые номера и числовые характеристики — `integer`.
  Временные отметки — `timestamp without time zone`: пояс источником не задан.
- Текст источника нормализуется через `NULLIF(BTRIM(value), '')` перед
  преобразованием. Пустой необязательный текст становится NULL. Опасное
  приведение предварительно проверяется; ошибки не скрываются фильтрацией.
- `NN` ниже означает `NOT NULL`; прочие поля допускают NULL. Ключи и FK должны
  быть реальными, проверенными ограничениями PostgreSQL. Отсутствующие факты
  не придумываются; дубликаты и сироты не устраняются скрытым `DISTINCT`.
- Исходные имена бизнес-полей сохраняются, включая `product_name_lenght` и
  `product_description_lenght`. `_source_file` и `_loaded_at` — поля `raw`,
  переносить их в модель не требуется.
- Модули выполняются общей транзакцией: без собственных `BEGIN`, `COMMIT`,
  `ROLLBACK`, `SAVEPOINT` и других команд управления транзакцией на верхнем
  уровне, любых команд psql с обратной косой чертой и операций, запрещённых
  в транзакции. `BEGIN` внутри `DO $$ ... $$` допускается. При ошибке
  необходимо завершить выполнение ненулевым кодом.

## Справочники — участник №3

### `core.categories`

Одна строка на исходный код категории товара плюс одна неизвестная категория.

| Поле | Тип | NULL | Источник и смысл |
|---|---|---|---|
| `category_code` | `text` | NN | PK; `raw.products.product_category_name` или `__unknown__` |
| `category_name_pt` | `text` | да | исходное португальское название; NULL для неизвестной |
| `category_name_en` | `text` | да | `raw.product_category_translation.product_category_name_english` |
| `is_translation_missing` | `boolean` | NN | true для известной категории без непустого английского перевода |

`__unknown__` не должен совпадать с реальным кодом. Для неизвестной категории
оба имени NULL, `is_translation_missing = false`; для отображения использовать
`COALESCE(category_name_en, category_name_pt, 'Unknown')`. Категории из товаров
без перевода сохраняются отдельно. Повторы/конфликты справочника переводов
исследовать, а не выбирать случайную строку.

## Показатели и официальные ответы

- Выручкообразующий заказ имеет `order_status = 'delivered'`; товарная выручка
  — `SUM(order_items.price)`, доставка в неё не входит.
- Чек заказа — сумма товаров и доставки по его позициям. Среднее считается по
  заказам после агрегации позиций и использует доставленные заказы. На текущем
  зерне одна позиция равна одной единице товара.
- Оплата — отдельная сумма платежей по заказу. Позиции, платежи и отзывы
  агрегируются независимо до соединения; `payment_installments` не множитель.
- Для отчёта по месяцам использовать месяц `order_purchase_timestamp`, период
  `[2016-09-01, 2018-09-01)`, календарь `generate_series`, число различных
  доставленных заказов и нули в месяцах без продаж.
- Для повторных покупок учитывать все статусы, считать различные `order_id`
  по `customer_unique_id`; повторный покупатель имеет не меньше двух заказов.
- Отчёты №2–5 используют весь набор данных, если в условии нет ограничения по
  дате. Для сверки двух результатов периоды и фильтры должны совпадать.
- Финальные денежные суммы и проценты выводятся с двумя знаками; деление на
  ноль даёт NULL. Округлённые доли категорий могут суммироваться не ровно в 100%.

| Вопрос | Владелец / файл | Поля результата | Контроль текущей выгрузки |
|---|---|---|---|
| 1 | №2, `queries/01_monthly.sql` | `month`, `orders_count`, `revenue` | 24 месяца, один нулевой, всего 13 221 498.11 |
| 2 | №4, `queries/02_top_sellers.sql` | `seller_id`, `seller_city`, `seller_state`, `orders_count`, `units_count`, `revenue` | 10 строк, лидер 226 987.93 |
| 3 | №2, `queries/03_average_check.sql` | `avg_order_value`, `avg_lines_per_order`, `avg_units_per_order` | средний чек 159.88 |
| 4 | №3, `queries/04_retention.sql` | `customers_total`, `repeat_customers`, `repeat_share_pct` | 96 096 покупателей, повторные 3.12% |
| 5 | №3, `queries/05_categories.sql` | `category`, `revenue`, `share_pct` | 74 категории, лидер 1 233 131.72, всего 13 221 498.11 |

Контрольные числа принадлежат проверкам и не подставляются в ответы или DDL.

## Витрины — участник №5

Обычные `VIEW` поверх `core`, без зависимостей от `raw`.

### `mart.order_financials`

Одна строка на каждый `core.orders.order_id`:

| Поле | Тип | NULL | Смысл |
|---|---|---|---|
| `order_id` | `text` | нет | идентификатор заказа |
| `customer_id` | `text` | нет | идентификатор записи покупателя |
| `order_status` | `text` | нет | статус |
| `purchase_month` | `date` | нет | первое число месяца оформления |
| `item_lines` | `bigint` | нет | число позиций |
| `item_units` | `bigint` | нет | число единиц, сейчас равно числу позиций |
| `items_amount` | `numeric` | нет | сумма товаров, без позиций = 0 |
| `freight_amount` | `numeric` | нет | сумма доставки, без позиций = 0 |
| `order_amount` | `numeric` | нет | товары + доставка |
| `payments_amount` | `numeric` | да | сумма платежей; нет записей = NULL |
| `is_revenue_order` | `boolean` | нет | статус `delivered` |

Сначала агрегировать позиции и платежи отдельно по `order_id`, затем соединять
их с заказами. Платёжные строки не умножают позиции.

### `mart.order_delivery`

Одна строка на каждый заказ. Сохраняются `order_id`, `order_status` и пять
одноимённых дат из `core.orders`, все в исходных типах и с исходной NULL-семантикой.

| Поле | Тип | NULL | Смысл |
|---|---|---|---|
| `days_purchase_to_delivery` | `numeric` | да | дни между оформлением и вручением; NULL, если нет даты или интервал отрицателен |
| `delivery_delay_days` | `integer` | да | дата вручения минус обещанная календарная дата для доставленных заказов с обеими датами |
| `is_late` | `boolean` | да | `delivery_delay_days > 0`; NULL, если задержка неизвестна |
| `has_incomplete_dates` | `boolean` | нет | хотя бы одна из пяти дат отсутствует; это не обязательно ошибка |
| `has_chronology_anomaly` | `boolean` | нет | известная дата вручения раньше известной даты оформления |

Отрицательная задержка означает раннюю доставку, а не ошибку. Неизвестную дату
не заменять нулевой длительностью. Для средних длительностей исключать NULL.

### `mart.seller_summary`

Одна строка на каждого продавца; продажи только по `delivered`.

| Поле | Тип | NULL | Смысл |
|---|---|---|---|
| `seller_id` | `text` | нет | продавец |
| `seller_city` | `text` | да | город |
| `seller_state` | `text` | да | штат |
| `orders_count` | `bigint` | нет | число различных заказов продавца |
| `units_count` | `bigint` | нет | число проданных позиций |
| `revenue` | `numeric` | нет | сумма цен его позиций |

Продавцы без продаж сохраняются с нулями. Заказ с несколькими продавцами
учитывается у каждого из них; число заказов по продавцам неаддитивно.

## Сборка, проверки и ответственность

После появления всех файлов и загрузки исходной базы команда из корня проекта:

```powershell
./scripts/build_model.ps1
# При ограничении политики запуска PowerShell:
powershell -ExecutionPolicy Bypass -File ./scripts/build_model.ps1
```

Раннер находит корень по своему пути, использует сервис `postgres` и по
умолчанию подключается к базе `marketplace` от имени `hack`. Для отдельной
тестовой базы можно передать `-Database` и `-User`. Отчёт каждого запуска
сохраняется в `%TEMP%/hackathon-model-build`; путь выводится в консоль.
При отсутствии любого обязательного файла модель не изменяется. Для
промежуточной проверки одного модуля необходимо самостоятельно подготовить
его зависимости; штатный раннер всегда проверяет весь комплект.

`model/00_schema.sql` → `model/10_dimensions.sql` →
`model/20_orders_items.sql` → `model/30_payments_reviews.sql` →
`model/40_marts.sql` → `tests/10_integrity.sql` →
`tests/20_reconciliation.sql` → `tests/30_marts.sql` → запросы `01`–`05`.

№1 проверяет ключи, ссылки, сохранение записей и неизменность `raw`; №4 —
денежные сверки и корректность соединений; №5 — зерно и результаты витрин.
Раннер сверяет число и контрольные суммы строк всех восьми таблиц `raw`, а
также снимок структуры схемы до и после SQL-файлов. На время сборки исходные
таблицы блокируются от одновременной записи другими сессиями. Проверка
целостности выводит контрольные суммы бизнес-полей `core` и суммы товаров,
доставки и платежей для сравнения отчётов двух сборок.
Полная пересборка — штатный повторный запуск. Каждый участник лично запускает
и проверяет свой SQL. Изменение контракта сначала согласуется со всеми
затронутыми владельцами и сопровождается повторным запуском старых проверок.
