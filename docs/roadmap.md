# Стратегия развития и архитектурного масштабирования хранилища данных Capibara

## Введение и инженерная позиция

Текущий объём данных маркетплейса Capibara составляет **550 759 строк** (99,4 тыс. заказов за 2 года).  
**Инженерный вердикт:** На текущем масштабе миграция на специализированные аналитические СУБД (ClickHouse, Greenplum, Snowflake) является необоснованной оверинженерией, которая кратно увеличит совокупную стоимость владения (TCO), усложнит контуры ETL/ELT и размоет консистентность транзакций.

Для текущего объёма используем **PostgreSQL 16**. Время выполнения запросов
и ограничения нагрузки нужно измерить на целевом оборудовании: универсального
гарантированного времени отклика для всех витрин здесь нет.

Масштабирование должно происходить эволюционно, на основе **объективных измерений метрик производительности**, а не абстрактных предположений.

## 2. Поэтапный план развития платформы данных

### Этап 1: Оптимизация текущего слоя PostgreSQL (Сейчас — Базовый уровень)
*Предел зависит от нагрузки, оборудования и требований к задержке, а не только от числа строк.*

1. **Индексы под измеренную нагрузку:**
   - Составной индекс на фильтры витрин:  
     `CREATE INDEX idx_orders_status_purchase ON core.orders (order_status, order_purchase_timestamp);`
   - Индекс для ускорения джойнов позиций и продавцов:  
     `CREATE INDEX idx_order_items_seller_order ON core.order_items (seller_id, order_id) INCLUDE (price);`
2. **Инкрементальное обновление витрин:**
   - На текущих 550 тыс. строк используются обычные `VIEW`.
   - При измеренной необходимости рассмотреть `MATERIALIZED VIEW` и частоту обновления. Для `REFRESH MATERIALIZED VIEW CONCURRENTLY` потребуется подходящий уникальный индекс и первичное заполнение.
3. **Партиционирование:**
   - Секционирование `core.orders` по `order_purchase_timestamp` рассматривать после измерений. В `core.order_items` этого поля сейчас нет: её секционирование потребует отдельного проектирования ключа и связей.

### Этап 2: Событийная модель и историчность данных (Event-Driven & SCD)

В текущем датасете Olist статусы представлены в виде плоских колонок дат (`approved_at`, `delivered_carrier_date` и т.д.).  
**Критическое ограничение:** Из текущей выгрузки **невозможно честно восстановить полную хронологию жизненного цикла** (например: повторные попытки вручения, возвраты, частичные отмены, изменение планового срока).

#### 1. Модель событий заказов (`core.order_events`):
Вместо перезаписи полей вводится неизменяемый лог событий:
```sql
CREATE TABLE core.order_events (
    event_id        uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id        text NOT NULL,
    event_type      text NOT NULL, -- 'created', 'paid', 'packed', 'carrier_transferred', 'out_for_delivery', 'delivered', 'canceled'
    event_time      timestamptz NOT NULL, -- когда событие произошло в физическом мире
    ingested_at     timestamptz NOT NULL DEFAULT now(), -- когда событие зафиксировано в DWH
    source_system   text NOT NULL, -- 'checkout_service', 'logistics_gateway', 'payment_broker'
    payload         jsonb -- дополнительные метаданные (код курьера, причина отмены)
);
CREATE INDEX idx_order_events_stream ON core.order_events (order_id, event_time);
```
*Разделение времени:* Чёткое разделение физического времени события (`event_time`) и системного времени фиксации (`ingested_at`) позволяет точно рассчитывать SLA и выявлять задержки передачи данных в шине.

#### 2. Разделение бизнес-процессов завершения заказа:
В модели необходимо строго разделить три несовместимых процесса:
- **Отмена заказа (Cancellation):** Заказ расторгнут до передачи перевозчику. Денежные средства разблокируются (холдирование снимается). Выручка не признаётся.
- **Возврат товара (Product Return):** После доставки товар возвращается; при наличии соответствующего процесса фиксируются возвратная накладная и изменение остатка. Сроки зависят от правил бизнеса и юрисдикции.
- **Возврат средств (Refund):** Финансовая транзакция обратного перечисления денег покупателю (может быть частичной при повреждении одной позиции).

#### 3. Версионирование измерений (SCD Type 2):
Для каталога товаров (`core.products`) и профилей продавцов (`core.sellers`):
- Добавление колонок `valid_from`, `valid_to`, `is_current`.
- Изменение юридического адреса продавца или категории товара не затирает историю: финансовые отчеты за 2017 год строятся по тарифам и состояниям 2017 года.

### Этап 3: Экосистема маркетплейса и единый профиль клиента

Маркетплейс Capibara эволюционирует в мультисервисную платформу (доставка, финтех, B2B-сервисы).

#### 1. Единый профиль клиента (Single Customer View / MDM):
В Olist уже заложено фундаментальное разделение:
- `customer_id` — транзакционный разовый токен сессии заказа;
- `customer_unique_id` — реальный сквозной идентификатор человека.

В экосистеме создаётся мастер-таблица сущности субъекта:
```sql
CREATE TABLE core.parties (
    party_id        uuid PRIMARY KEY,
    party_type      text NOT NULL CHECK (party_type IN ('individual', 'legal_entity')),
    tax_identifier  text UNIQUE, -- CPF / CNPJ (Бразилия) в зашифрованном виде
    created_at      timestamptz NOT NULL
);

-- Роли субъекта в экосистеме (один и тот же человек может быть и покупателем, и продавцом):
CREATE TABLE core.party_roles (
    party_id        uuid REFERENCES core.parties(party_id),
    role_type       text NOT NULL CHECK (role_type IN ('buyer', 'seller', 'driver', 'partner')),
    role_entity_id  text NOT NULL, -- ссылка на customer_unique_id или seller_id
    PRIMARY KEY (party_id, role_type, role_entity_id)
);
```

#### 2. Защита конфиденциальных данных (PII & Security):
- Разделение профиля клиента: контактные данные (ФИО, телефон, точный адрес) хранятся в защищенной схеме `secure_core` с ограничением прав доступа по ролям (RBAC).
- В аналитический слой `mart` передаются исключительно деперсонализированные идентификаторы (`customer_unique_id`), гео-агрегаты (город, штат, zip-prefix) и поведенческие метрики.

#### 3. Реалистичные межсервисные гипотезы:
Кросс-сценарные связки (например, рекомендации товаров для путешествий или интеграция с автосервисами) моделируются только при наличии **реальных подтвержденных событийных связей** между смежными сервисами, а не искусственным объединением разнородных сущностей в одну широкую таблицу с сотней nullable-полей.

### Этап 4: Аналитическое масштабирование (ClickHouse / Lakehouse)

При измеренном нарушении SLA и конкуренции за ресурсы между оперативной нагрузкой и отчётами можно рассмотреть выделение аналитического хранилища; фиксированного порога по числу строк нет.

#### 1. Целевая архитектура DWH:
- **OLTP-слой (PostgreSQL):** обработка транзакций оформления, платежей и статусов.
- **Шина данных (Apache Kafka + Debezium):** захват изменений (CDC) из WAL PostgreSQL без нагрузки на базу.
- **OLAP DWH (ClickHouse):** колоночное хранилище для витрин `mart` с движками `ReplacingMergeTree` и `SummingMergeTree`.

#### 2. План безопасного перехода (Migration Blueprint):
1. **Двойная запись (Dual Run):**
   Витрины строятся параллельно в PostgreSQL и в ClickHouse в течение 1–2 отчётных периодов.
2. **Сверка метрик (Reconciliation Pipeline):**
   Автоматизированный скрипт ежесуточно сверяет контрольные суммы: `SUM(gmv)`, `COUNT(orders)` между Postgres и ClickHouse. Допустимое отклонение: **0.00%**.
3. **Исторический Backfill:**
   Пакетная выгрузка исторических срезов через Parquet-файлы с проверкой хэш-сумм блоков.
4. **План отката (Rollback Strategy):**
   Аналитические дашборды сохраняют конфигурацию переключения DataSource обратно на PostgreSQL-реплику одной переменной окружения в случае деградации или сбоя в ClickHouse.

## 3. Перспектива расширенной аналитики (P2): Market Basket Analysis

Полезное расширение аналитического слоя — анализ совместных покупок (товары и категории, приобретаемые вместе в рамках одного чека).

### Реализация на SQL (без внешних ML-библиотек):
```sql
-- Анализ частых пар категорий в мультипозиционных заказах
WITH order_categories AS (
    SELECT DISTINCT
        oi.order_id,
        p.category_code AS category_name
    FROM core.order_items oi
    JOIN core.orders o ON oi.order_id = o.order_id
    JOIN core.products p ON oi.product_id = p.product_id
    WHERE o.order_status = 'delivered'
),
category_pairs AS (
    SELECT
        c1.category_name AS category_a,
        c2.category_name AS category_b,
        COUNT(DISTINCT c1.order_id) AS co_occurrence_count
    FROM order_categories c1
    JOIN order_categories c2
      ON c1.order_id = c2.order_id
     AND c1.category_name < c2.category_name -- исключение дублей и зеркальных пар
    GROUP BY c1.category_name, c2.category_name
)
SELECT
    category_a,
    category_b,
    co_occurrence_count,
    ROUND(
        (100.0 * co_occurrence_count /
         (SELECT COUNT(DISTINCT i.order_id)
          FROM core.order_items i JOIN core.orders o ON o.order_id = i.order_id
          WHERE o.order_status = 'delivered'))::numeric,
        3
    ) AS pair_support_pct
FROM category_pairs
ORDER BY co_occurrence_count DESC
LIMIT 10;
```

**Бизнес-применение:**
- Формирование товарных бандлов на витрине («Вместе дешевле»).
- Размещение совместных категорий на одном складе для оптимизации логистической упаковки (снижение числа отправок от разных продавцов).
- Данный функционал предлагается как понятная детерминированная эвристика без декларации неподтвержденных «ИИ-рекомендаций».
