# Метрики покупателей и категорий

Документ описывает правила, по которым считаются официальные вопросы №4 и №5.
Используется командой (особенно №5 — для дашборда) и руководителем — для презентации.

## 1. Два клиентских идентификатора

В `core.customers` живут два разных ID, и их нельзя путать:

| Поле | Роль | Уникальность |
|---|---|---|
| `customer_id` | Идентификатор **записи** о клиенте в рамках конкретного заказа. Именно на него ссылается `core.orders.customer_id`. | PK, уникален (99 441 строк). |
| `customer_unique_id` | Обезличенный сквозной идентификатор **покупателя в наборе данных**. Для нескольких заказов одного покупателя могут встречаться разные `customer_id` и один `customer_unique_id`. | НЕ уникален в `core.customers`. Используется для группировки повторных покупок. |

**Диагностика:** 99 441 строк / 99 441 `customer_id` / 96 096 `customer_unique_id`.
Если в отчёте получается 99 441 «уникальных покупателей» — значит, ошибочно сгруппировали по `customer_id`. Правильный ответ — **96 096**.

## 2. Что считается «покупкой» (вопрос №4)

Для этого вопроса покупка = оформленный заказ любого статуса. Это правило
соответствует контрольному числу 96 096; статус `delivered` применяется к
товарной выручке, а не к этому числу покупателей.

Повторный покупатель = идентификатор `customer_unique_id`, у которого **≥ 2 разных заказов**.

Формулы:
- `customers_total` = `COUNT(DISTINCT customer_unique_id)` среди всех заказов.
- `repeat_customers` = количество таких людей, у кого `COUNT(DISTINCT order_id) >= 2`.
- `repeat_share_pct` = `repeat_customers / customers_total * 100`, с защитой от деления на ноль через `NULLIF`.

Контроль: **96 096** покупателей, **3,12%** повторных.

### Неаддитивность по времени и категориям
`repeat_customers` — это свойство идентификатора покупателя за весь период, а не за месяц/категорию.
Если разбить покупателей по месяцу заказа или категории, покупатель может попасть
в несколько групп. Для всего периода людей нужно дедуплицировать, а процент
пересчитывать по числителю и знаменателю. Когорты по месяцу **первого** заказа
не пересекаются, если каждому покупателю назначен единственный первый месяц.

## 3. Справочник категорий и fallback-правила (вопрос №5)

Источник: `raw.products` (уникальные `product_category_name`) + `raw.product_category_translation` (71 строка).

Правила формирования `core.categories`:
1. Берём все уникальные категории из `products`.
2. LEFT JOIN на `product_category_translation`.
3. Если перевода нет, `category_name_en` остаётся NULL, `is_translation_missing = true`; при отображении используется португальское название.
4. Если `product_category_name` = NULL или пустая строка — `category_code = '__unknown__'`, оба названия NULL, а отображаемое имя — `Unknown`. Зарезервированный код проверяется на отсутствие в источнике.

Итог текущей выгрузки: **74 категории** (71 с переводом, 2 без перевода и `__unknown__`).

При JOIN `order_items → products → categories` ни одна позиция не теряется:
- у товара без категории — категория `__unknown__`;
- у товара с категорией без перевода — остаётся португальское имя.

## 4. Выручка по категориям (вопрос №5)

- База: `core.order_items` × `core.orders` × `core.products` × `core.categories`.
- Фильтр: `order_status = 'delivered'` (общее правило).
- Выручка категории = `SUM(core.order_items.price)` по зерну позиции.
- `freight_value` и `payment_value` НЕ включаются — это отдельные сущности (логистика и платежи), они не относятся к выручке продавца за товар.
- `overall_revenue` = сумма `revenue` по всем 74 категориям из того же набора. Это гарантирует, что `SUM(share_pct) ≈ 100%` с учётом округления.

Формулы:
- `revenue` = `ROUND(SUM(price)::numeric, 2)`
- `share_pct` = `ROUND(revenue / overall_revenue * 100, 2)`

Контроль:
- категорий: **74**
- топ-1: **1 233 131.72**
- сумма: **13 221 498.11**

## 5. Ограничения и известные особенности

- Все исходные поля в `raw` — `text`. Числовые поля в `core.products` приводятся через `NULLIF(BTRIM(...), '')::INTEGER`, поэтому пустые строки и NULL остаются NULL, а не превращаются в 0.
- Исходные имена `product_name_lenght` и `product_description_lenght` сохранены в `core.products` согласно контракту.
- ZIP-коды (`customer_zip_code_prefix`, `seller_zip_code_prefix`) хранятся как `text`, чтобы не терять ведущие нули.
- Отдельные справочники городов/штатов не создавались — в данных нет неоднозначных FK, а уникальность пар (city, state) не проверялась как обязательное условие.
